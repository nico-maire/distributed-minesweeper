# Distributed Minesweeper — Distributed Systems Project

A fault-tolerant, multiplayer minesweeper game built on a **replicated state machine** backed by a Leader–Follower chain using a two-phase PREPARE/COMMIT replication protocol over TCP sockets.

## Architecture

### Replicated State Machine (SMR)

The backend implements **State Machine Replication**. Every game room evolves through a totally ordered sequence of commands generated by the leader. Replicas that start from the same initial state and apply the same command sequence in the same order converge to identical state.

Each command carries a monotonically increasing `seq` number. `GameStateMachine.apply_command()` validates strict sequential ordering — duplicate or out-of-order commands are rejected at the state-machine level.

### Module Responsibilities

| Module | Responsibility |
|--------|---------------|
| `replication.py` | `ChainReplicationManager` — owns the socket to the next replica, the ACK table, and the PREPARE/COMMIT protocol. Shared between follower and promoted-leader phases to avoid the race condition of two threads reading the same socket. |
| `follower_runtime.py` | `FollowerRuntime` — processes PREPARE/COMMIT from the upstream; forwards through the chain; applies on COMMIT; discards pending_ops on exit. |
| `promoted_leader_runtime.py` | `PromotedLeaderRuntime` — handles client connections after promotion; replicates via the same `ChainReplicationManager` instance. |
| `state_machine.py` | `GameStateMachine` — applies commands deterministically; enforces `seq == last_committed_seq + 1`. |
| `room_manager.py` | `RoomManager` — maps rooms to client sockets and usernames; `broadcast_to_room` snapshots the socket list before releasing the lock to avoid holding it during potentially blocking sends. |

### Two-Phase PREPARE/COMMIT Chain

```
Client
  │  action (reveal / flag / restart)
  ▼
Leader (port 5000)
  │  PREPARE_COMMAND(seq, op_id, command)
  ▼
Follower-1 (port 6000)
  │  PREPARE_COMMAND(seq, op_id, command)
  ▼
Follower-2 (port 7000)
  │  PREPARE_ACK(op_id)
  ▲
Follower-1  ← applies locally on COMMIT
  │  PREPARE_ACK(op_id)
  ▲
Leader
  │  COMMIT_COMMAND(seq, op_id)
  ▼
Follower-1
  │  COMMIT_COMMAND(seq, op_id)
  ▼
Follower-2  ← applies locally
  │  COMMIT_ACK(op_id)
  ▲
Follower-1
  │  COMMIT_ACK(op_id)
  ▲
Leader  ← applies locally → broadcasts UPDATE_ROOM to clients
```

**A client operation is confirmed only after all three nodes have committed it.**

### Deterministic Boards

When a room is created (or restarted), the leader generates a random `seed` and includes it in the command. All replicas initialize their `Minesweeper` object with the same seed, guaranteeing identical mine layouts across the cluster without any coordination beyond the command log.

### User Session Replication

Active user sessions (`UPDATE_USERS` — join/leave) are replicated fire-and-forget to the follower: they do **not** go through PREPARE/COMMIT. This is a deliberate design choice: user-list state is transient and is automatically reconstructed when clients rejoin after a failover. Decoupling user-list updates from the two-phase protocol prevents unnecessary latency and simplifies the critical path.

### Fault Tolerance

| Scenario | Behaviour |
|----------|-----------|
| Leader crashes after commit | Follower-1 promotes; all committed state fully intact |
| Leader + Follower-1 crash after commit | Follower-2 retains committed state; promotes to leader |
| Follower-2 unreachable during PREPARE | Operation rejected; client receives `error` response |
| Leader crashes before commit | Pending ops discarded on F1 promotion; client must retry |

### Degraded Mode

When Follower-2 is the last surviving node, it operates in **degraded mode**: the `ChainReplicationManager` has no next replica, so `replicate()` returns `True` immediately (solo mode). Writes are still accepted but are no longer replicated — the cluster has zero fault tolerance remaining. This is a deliberate availability-over-consistency trade-off for the last node standing. If strict consistency is required even in this state, the node should refuse writes; the current implementation prefers availability to allow the game to continue.

### Sequence Validation

`GameStateMachine.apply_command()` enforces `seq == last_committed_seq + 1` before applying any command. Duplicate commands (`seq ≤ last_committed_seq`) are silently ignored (idempotent). Out-of-order or gapped commands raise `ValueError`, signalling a protocol violation.

### Failover and Client Reconnection

When the upstream connection closes, a follower discards all uncommitted `pending_ops` and promotes to leader. The client tries each node in order (leader → follower-1 → follower-2) and re-sends a `join` message to rebuild the session.

### Multiplayer Rooms

Players join isolated game rooms by name. Broadcasts are strictly scoped per room. Multiple rooms run concurrently on the same cluster.

## How to Run

### Full containerised stack (recommended)

On Linux, allow Docker to connect to the local X display, then bring up the full stack:

```bash
xhost +local:docker
docker compose up --build
```

This starts `leader`, `follower-1`, `follower-2`, and a `frontend` container. The GUI window will appear on your desktop.

### Backend only (for development or testing)

```bash
docker compose up --build leader follower-1 follower-2
```

Then run the client natively:

```bash
python frontend/client.py
```

## Integration Tests

The test suite uses real OS processes and verifies the following guarantees:

| # | File | Test | Guarantee verified |
|---|------|------|--------------------|
| 1 | `test_replication.py` | `test_all_replicas_same_state` | All three replicas share `last_committed_seq` and board after a commit |
| 2 | `test_failover.py` | `test_operation_survives_leader_crash` | Confirmed move survives leader crash; F1 serves correct state |
| 3 | `test_failover.py` | `test_operation_survives_leader_and_f1_crash` | Confirmed move survives leader + F1 crash; F2 retains state |
| 4 | `test_failover.py` | `test_f2_accepts_clients_after_both_crashes` | F2 promotes and serves actual client connections after both crashes |
| 5 | `test_consistency_failures.py` | `test_no_confirm_if_f2_down` | With F2 down, leader must not confirm the operation |
| 6 | `test_consistency_failures.py` | `test_uncommitted_op_discarded_after_failover` | Pending (PREPARE-only) op is discarded when F1 promotes |
| 7 | `test_multiplayer_rooms.py` | `test_two_clients_same_room` | Two clients in the same room see identical board updates |
| 8 | `test_multiplayer_rooms.py` | `test_room_isolation` | A reveal in roomA does not affect roomB |
| 9 | `test_replication.py` | `test_operation_order_preserved` | Successive operations advance `last_committed_seq` monotonically across all replicas |

Run with:

```bash
cd tests
python -m pytest test_replication.py test_failover.py test_consistency_failures.py test_multiplayer_rooms.py -v
```

## CAP Theorem Trade-off

This system prioritises **Consistency** over **Availability** (CP profile). When a replica is unreachable, the operation is rejected rather than accepted with partial replication. The cluster remains consistent but sacrifices availability when part of the replica chain fails.

The sole exception is the **degraded mode** described above: when only one replica survives, availability is preferred to allow gameplay to continue — but the system explicitly documents that no fault tolerance remains.
