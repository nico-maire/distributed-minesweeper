# Distributed Minesweeper — Distributed Systems Project

A fault-tolerant, multiplayer minesweeper game built on a **replicated state machine** backed by a Leader–Follower chain using a two-phase PREPARE/COMMIT replication protocol over TCP sockets.

## Architecture

### Replicated State Machine (SMR)

The backend implements **State Machine Replication**. Every game room evolves through a totally ordered sequence of commands generated by the leader. Replicas that start from the same initial state and apply the same command sequence in the same order converge to identical state.

```
Client
  │  action (reveal / flag / restart)
  ▼
Leader (port 5000)
  │  PREPARE_COMMAND(seq, op_id, command)
  ▼
Follower-1 (port 6000)
  │  PREPARE_COMMAND(seq, op_id, command)
  ▼
Follower-2 (port 7000)
  │  PREPARE_ACK(op_id)
  ▲
Follower-1
  │  PREPARE_ACK(op_id)
  ▲
Leader
  │  COMMIT_COMMAND(seq, op_id)
  ▼
Follower-1
  │  COMMIT_COMMAND(seq, op_id)
  ▼
Follower-2  ←── applies command
  │  COMMIT_ACK(op_id)
  ▲
Follower-1  ←── applies command
  │  COMMIT_ACK(op_id)
  ▲
Leader      ←── applies command → broadcasts update_room to clients
```

**A client operation is confirmed only after all three nodes have committed it.** This means:
- Any confirmed move survives the sequential failure of the leader and follower-1.
- If either follower is unreachable during PREPARE, the operation is rejected and the client is notified.

### Deterministic Boards

When a room is created (or restarted), the leader generates a random `seed` and includes it in the `create_room` / `restart` command. All replicas initialize their `Minesweeper` object with the same seed, guaranteeing identical mine layouts across the cluster without any coordination beyond the command log.

### Fault Tolerance

| Scenario | Behaviour |
|----------|-----------|
| Leader crashes after commit | Follower-1 promotes; state fully intact |
| Leader + Follower-1 crash after commit | Follower-2 retains the committed state |
| Follower-2 unreachable during PREPARE | Operation rejected; client gets `error` |
| Leader crashes before commit | Pending ops discarded on promotion; client retries |

### Failover and Client Reconnection

When the leader socket closes, a follower discards all uncommitted `pending_ops` and starts accepting client connections. The client tries each node in order (leader → follower-1 → follower-2) and re-sends a `join` message to rebuild the session.

### Multiplayer Rooms

Players join isolated game rooms by name. Broadcasts are strictly scoped per room. Multiple rooms run concurrently on the same cluster.

## How to Run

### Full containerised stack (recommended)

On Linux, allow Docker to connect to the local X display, then bring up the full stack:

```bash
xhost +local:docker
docker compose up --build
```

This starts `leader`, `follower-1`, `follower-2`, and a `frontend` container. The GUI window will appear on your desktop.

### Backend only (for development or testing)

```bash
docker compose up --build leader follower-1 follower-2
```

Then run the client natively:

```bash
python frontend/client.py
```

## Integration Tests

The test suite (`tests/test_integration.py`) spawns real OS processes and verifies the following guarantees:

| # | Test | Guarantee verified |
|---|------|--------------------|
| 1 | `test_all_replicas_same_state` | All three replicas share the same `last_committed_seq` and board after a confirm |
| 2 | `test_operation_survives_leader_crash` | A confirmed move survives leader crash; F1 serves the correct state |
| 3 | `test_operation_survives_leader_and_f1_crash` | A confirmed move survives leader + F1 crash; F2 retains the state |
| 4 | `test_no_confirm_if_f2_down` | With F2 down the leader must not confirm the operation to the client |
| 5 | `test_uncommitted_op_discarded_after_failover` | A pending (PREPARE-only) op is discarded when F1 promotes |
| 6 | `test_two_clients_same_room` | Two clients in the same room see identical board updates |
| 7 | `test_room_isolation` | A reveal in roomA does not affect roomB |
| 8 | `test_operation_order_preserved` | Successive operations advance `last_committed_seq` monotonically across replicas |

Run with:

```bash
cd tests
python -m pytest test_integration.py -v
```

## CAP Theorem Trade-off

This system prioritises **Consistency** over **Availability**. When a replica is unreachable, the operation is rejected rather than accepted with partial replication. This matches a **CP** profile: the cluster remains consistent but sacrifices availability when part of the replica chain fails.
